課題

データベースは PII の在庫です。

HTTPS は通信中を守ります。しかし DB ダンプ、盗まれたバックアップ、リードレプリカ、SQL インジェクションは保存時の顧客メールやユーザーデータを露出します。フィールド自体を暗号化しない限り。

Laravel デフォルト

メールが平文で残る

users テーブル、パスワードリセット、バックアップ、エクスポートに読めるメールアドレスが含まれます。

ハッシュだけでは不十分

ログインと一意性が壊れる

一方向ハッシュは値を守りますが、大文字小文字を無視したログイン、リセット検索、重複登録が必要です。

自作暗号

移行とローテーションが危険

独自のキー管理は、既存データ、キーローテーション、ロールバックを誤りやすくします。

得られるもの

アプリを書き換えるのではなく、小さな Laravel パッケージで解決します。

保存時

DB ダンプで PII を読めない

宣言したフィールドは enc:v1:… として保存され、キーは環境変数またはシークレット管理に残ります。

書き換え不要

Eloquent はそのまま

$user->email、getAttribute()、通知、メールは平文を受け取ります。

認証維持

ログインとリセットが動く

Auth::attempt()、パスワードリセット、通知が暗号化メールを安全に扱います。

検索

ブラインドインデックス検索

大文字小文字を無視した完全一致検索を email_bidx で実現し、登録時の一意性も保証します。

運用

既存データ移行とローテーション

既存行の暗号化、インデックス補完、キーローテーションを Artisan コマンドとドライランで実行。

オープンソース

GPL-2.0、ロックインなし

ソース、変更履歴、リリースは GitHub。管理画面やキー預託はなく、キーはあなたのもの。

実際の Laravel アプリで dogfood

Laravel 12 アプリで User と Customer モデルを使い、マイグレーション、認証、パスワードリセット、バックフィル、キーローテーションまで実行しました。

Dogfood では長いメール、大文字小文字を無視したログイン、重複の一意性、リセット通知、既存行のバックフィル、2 モデルのキーローテーションも検証しました。

仕組み

デフォルト拒否: 設定に列挙したフィールドだけを暗号化。コアパッチもフレームワークの強制変更もありません。

▦

1 つの設定マップ

モデルごとに最大 20 フィールドを、任意のインデックスと正規化設定と一緒に列挙。

🔐

AES-256-GCM

ランダム化された認証付き暗号化。各ペイロードにキー ID を保存してローテーション可能。

🔎

ブラインドインデックス

正規化した値とフィールド名の HMAC-SHA256。インデックスに平文を保存せず完全一致検索。

👤

メールログイン

カスタムユーザープロバイダーがメール認証情報を暗号化メールのインデックスへ変換。

🔁

パスワードリセット

encrypted-database ブローカードライバーがリセットトークン表にブラインドインデックスを保存。

🧰

運用

ステータス、ドライラン付きバックフィル、キーローテーション、チャンク設定、マイグレーション公開。

インストール

PHP 8.1+、Laravel 10/11/12、OpenSSL が必要です。既存行を暗号化する前に DB をバックアップしてください。

01

GitHub VCS パッケージを追加し、設定とマイグレーションを公開。

02

キーリング、トークンシークレット、モデルのフィールドマップを設定。

03

バックフィルし、認証/パスワードドライバーを切り替えてログインをテスト。

composer config repositories.encrypted-fields vcs https://github.com/thiennhant95/laravel-encrypted-fields
composer require thiennhant95/laravel-encrypted-fields:^0.1

php artisan vendor:publish --tag=encrypted-fields-config
php artisan vendor:publish --tag=encrypted-fields-migrations
php artisan migrate

# .env
ENCRYPTED_FIELDS_KEY=base64:REPLACE_WITH_32_BYTE_KEY
ENCRYPTED_FIELDS_KEY_ID=main
ENCRYPTED_FIELDS_TOKEN_SECRET=REPLACE_WITH_A_STABLE_SECRET

FAQ

導入前のよくある質問

email 列も暗号化されますか？

はい。email 自体が AES-256-GCM の暗号文になり、別の email_bidx 列に正規化した HMAC を保存して完全一致検索と一意性を維持します。

ログインとパスワードリセットは動きますか？

はい。カスタムユーザープロバイダーがログイン認証情報を email_bidx に変換し、暗号化パスワードブローカーがリセットトークンに平文メールを残しません。

メールの部分一致検索はできますか？

いいえ。ブラインドインデックスは完全一致のみです。部分一致 LIKE 検索には別のトークンインデックスが必要で、このパッケージの範囲外です。

メールの一意性はどう検証しますか？

保存される email が暗号文のため、Laravel 標準の unique:users,email の代わりに EncryptedUnique(User::class, 'email') を使います。

キーをなくしたら？

キーなしでは暗号化値を復元できません。キーリングを DB 外にバックアップし、変更前にローテーションを演習してください。

20 フィールドまで暗号化できますか？

はい。モデルマップに任意の数のフィールドを追加できます。index があるフィールドは検索可能、ないフィールドは暗号化のみです。

無料ですか？

はい。GPL-2.0-or-later、ソースとリリースは GitHub。有料プラン、テレメトリー、キー預託はありません。
